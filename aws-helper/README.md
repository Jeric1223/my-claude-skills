# aws-helper

AWS를 조회할 때 **어떤 자격증명으로 볼지 먼저 정하고**, 쓰기는 실행하지 않고 명령어만 넘기는 스킬.

## 왜 만들었나

`~/.aws/credentials`에 프로파일이 여러 개 쌓여 있고, 각각 권한이 좁게 갈려 있는 상황에서 출발했다. DynamoDB를 읽을 수 있는 프로파일과 테이블을 수정할 수 있는 프로파일이 다르고, 람다 코드를 받을 수 있는 프로파일은 IAM을 못 본다. 그래서 조회를 시킬 때마다 AccessDenied가 나고, 그게 **권한이 없어서인지 프로파일을 잘못 골라서인지** 매번 처음부터 다시 확인해야 했다.

"그럼 각 프로파일 권한을 읽어서 알려주면 되지 않나" 싶었는데, 실제로 확인해보니 **모든 프로파일이 자기 IAM 정책 조회에서 AccessDenied**였다.

```
[profile-a] AccessDenied ... ListAttachedUserPolicies
[profile-b] AccessDenied ... ListAttachedUserPolicies
[profile-c] AccessDenied ... ListAttachedUserPolicies
```

최소 권한으로 발급된 키라면 흔한 상황이다. 권한 목록을 물어보는 길이 막혀 있으니, **실제로 명령을 던져본 결과를 쌓는 것** 말고는 방법이 없었다. 이 스킬은 그 누적 기록을 캐시로 관리해서, 쓸수록 프로파일 선택 질문이 줄어들도록 설계했다.

## 설계 결정

**권한 정보는 캐시에 쌓고, 빈칸만 프로브한다.** 매번 전 프로파일을 프로브하면 질문 하나당 수 초에서 십수 초가 붙는다. 캐시를 먼저 보고 기록이 없는 것만 던진다. 첫 회는 느리고 쓸수록 빨라진다.

**"기록 없음"과 "권한 없음"을 구분한다.** 캐시에 없다고 안 되는 게 아니다. 이걸 뭉개면 실제로는 가능한 조회를 "권한이 없습니다"라고 잘못 보고하게 된다.

**캐시는 레포 밖(`~/.claude/aws-profile-capabilities.json`)에 둔다.** 계정 ID와 사용자 ARN이 들어가므로 저장소에 올라가면 안 된다. 스킬 문서에도 실제 계정·프로파일명을 적지 않는다 — 런타임에 캐시를 읽으므로 문서에는 필요 없다.

**확신할 때만 자동 선택한다.** 후보가 딱 하나면 묻지 않고 진행하되 어떤 프로파일을 썼는지 항상 한 줄로 밝힌다 — 조회 결과의 신뢰도가 프로파일에 달려 있기 때문이다. 후보가 둘 이상이거나 기록이 없으면 묻는다.

**쓰기 판정은 화이트리스트로 한다.** `describe-*` `get-*` `list-*` 등 읽기로 확인된 것만 통과시키고 나머지는 전부 쓰기로 본다. 블랙리스트로 하면 새 AWS 명령이 생길 때마다 구멍이 뚫린다. 오탐(읽기를 쓰기로 봄)은 한 번 더 묻고 끝나지만 놓치면 되돌릴 수 없다.

**쓰기는 실행하지 않는다.** 명령어와 예상 영향, 롤백 방법을 만들어 넘기고 실행은 사람이 한다.

**계정이 다르면 무조건 묻는다.** 프로파일이 여러 계정에 걸쳐 있을 때 맥락만 보고 자동 선택하면 엉뚱한 환경을 보고 보고하게 된다.

## 사용 흐름

```
"이 람다 환경변수 뭐 들어있어?"
  → 캐시 조회: lambda:GetFunctionConfiguration 가능한 프로파일이 하나
  → "<프로파일명>으로 조회합니다" + 결과

"이 테이블 스트림 켜줘"
  → 쓰기 감지 → 실행하지 않음
  → 쓰기 권한이 확인된 프로파일 + 완성된 명령어 + 롤백 방법 제시
```

## 상태

**첫 초안이고 실사용으로 검증되지 않았다.** 캐시가 의도대로 누적되는지, 쓰기 판정에 오탐·누락이 없는지는 몇 번 써보면서 다듬어야 한다.
