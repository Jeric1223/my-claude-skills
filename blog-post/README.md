# blog-post

레포에서 **글로 남길 만한 것**을 찾아 후보를 제안하고, 고른 주제로 기술 블로그 초안을 만듭니다. 화면은 실제로 캡처해서 넣고, 마지막에 AI 티를 벗깁니다.

```
/blog-post
```

## 무엇을 하나

1. **글감 발굴** — git 히스토리에서 마찰의 흔적을 찾습니다. revert·재수정 커밋, 통째로 갈아엎은 구조, 유난히 자주 손댄 파일, 새로 들어온 의존성. 기능 목록이 아니라 "예상과 달랐던 것"을 찾습니다.
2. **후보 제안** — 3~4개를 제목안·줄거리·근거 커밋과 함께 물어봅니다. 쓸 게 없으면 없다고 합니다.
2.5. **인터뷰** — 후보를 전부 거절하거나 회고·소개 성격의 글을 원하면, 후보를 다시 뽑지 않고 질문으로 전환합니다.
3. **사실 수집** — 고른 주제에 대해 실제 코드·커밋·설정을 읽습니다. 확인된 것과 확인 못 한 것을 나눠 관리합니다.
4. **스크린샷** — `claude-in-chrome`으로 새 탭을 열어 캡처합니다. README용 캡처는 `readme-screenshots` 쪽입니다. 폭을 고정해서 샷 크기를 맞추고, 실계정·토큰이 찍혔는지 확인합니다.
5. **초안** — `style.md`의 문체(합니다체, 짧은 문단)로 `template.md`의 번호 섹션 골격을 채웁니다.
6. **AI 티 제거** — `humanize-korean`에 넘깁니다.
7. **점검** — 이미지 수, 제목 밀도, 플레이스홀더 잔존을 `grep`으로 셉니다.
8. **소개문** — 목록 카드에 뜰 150자 이내 요약을 같이 만듭니다.

## 왜 이렇게 설계했나

### 없는 사실을 만들지 않는다

글감을 키우다 보면 구체적인 숫자가 아쉬워집니다. "이틀은 아꼈다", "3배 빨라졌다" 같은 문장은 글을 그럴듯하게 만들지만, 근거가 없으면 그냥 거짓말입니다. 실제로 초안을 만들다 없는 기간과 없는 리전명을 넣은 적이 있습니다.

그래서 **확인된 사실은 파일·줄 번호와 함께, 확인 못 한 것은 본문이 아니라 "직접 채울 것" 목록으로** 분리합니다. 빈칸이 틀린 값보다 낫습니다.

### AI 티를 벗기다가 가독성을 죽이지 않는다

AI가 쓴 글은 이모지가 문장마다 붙고, 굵게+콜론 불릿이 연속되고, 표가 남발됩니다. 그래서 이걸 전부 걷어내면 문체는 자연스러워집니다 — 그리고 **아무도 안 읽는 텍스트 벽**이 됩니다.

문제는 이 장치들이 *남발*된 거지 존재한 게 아닙니다. 훑어읽는 독자에게는 붙잡을 앵커가 필요합니다. 그래서 정량 게이트를 둡니다.

| 항목 | 기준 |
| :--- | :--- |
| 이미지 | 기능 섹션마다 1장 |
| 문단 길이 | 1~2문장, 문장마다 줄바꿈 |
| 섹션 | 번호 제목, 사이에 `---` |
| 코드블록 | 구조도 위주, 구현 코드는 15줄 이내 |
| 굵게 | 섹션당 1~2회 |
| 이모지 | 서비스 링크 줄에만 |

`humanize-korean`을 통과한 **뒤에** 이 게이트를 다시 확인합니다. 윤문 과정에서 시각 요소가 깎이기 때문입니다.

기준이 "문단 5개"가 아니라 "한 화면"인 이유가 있습니다. velog·티스토리는 단이 좁아서, 에디터에서 4줄이던 문단이 발행본에선 8줄이 됩니다. 원고에서 멀쩡해 보이던 구간이 실제로는 스크롤 한 번이 통째로 글자입니다. 그래서 발행 후 실제 페이지를 한 번 내려보라고 안내합니다.

### 친절한 개발기 문체로 쓴다

기준은 [NULL지마 개발기](https://velog.io/@donghyuk65/%EC%84%A4%EC%B9%98-%EC%97%86%EC%9D%B4-SQL%EC%9D%84-%EC%97%B0%EC%8A%B5%ED%95%A0-%EC%88%98-%EC%9E%88%EB%8A%94-%EC%9B%B9-%EC%84%9C%EB%B9%84%EC%8A%A4-NULL%EC%A7%80%EB%A7%88-%EA%B0%9C%EB%B0%9C%EA%B8%B0)입니다. 합니다체로 쓰고, 독자가 했을 법한 말을 인용하며 시작합니다. 내 경험을 거쳐 "그래서 만들게 된 프로젝트가 바로 X입니다"로 넘어가고, 그 뒤로 기획 의도 → 기능 → 기술 → 느낀 점 → 개선 → 마무리 순서를 따릅니다. 섹션마다 "상황 한두 문장 → 다음과 같습니다 + 불릿 → 의도 한 문장" 리듬을 반복합니다.

예전 글(루프런)은 해요체에 기술 디테일이 많고 회고가 없었습니다. 어떻게 고쳐 쓰는지는 `style.md`에 예문으로 있습니다.

### 레포에 없는 것은 물어본다

글감 발굴은 git 히스토리를 봅니다. 그래서 "무엇이 예상과 달랐나"는 잘 찾지만, **"왜 이걸 만들었고 무엇을 느꼈나"는 못 찾습니다.** 회고나 프로젝트 소개를 쓰려는 사람에게 마찰 기반 후보를 네 개 던지면 전부 거절당합니다. 실제로 그랬습니다.

이때 후보를 다시 뽑는 건 소용이 없습니다. 같은 데이터에서 같은 성격의 후보가 또 나옵니다. 그래서 **인터뷰로 전환**합니다. 독자와 결론 한 문장을 먼저 못 박고, 서너 개씩 묶어서 묻습니다.

질문은 의견이 아니라 **장면**을 부르는 쪽이 낫습니다. "이 프로젝트의 의의는?"에는 누구나 할 수 있는 말이 돌아오고, "이걸 쓰기 전에는 그 작업을 어떻게 하셨나요?"에는 그 사람만 아는 이야기가 돌아옵니다. 그리고 그 답변은 **요약하지 않고 소재로** 씁니다. 매끄럽게 다듬다가 사용자가 든 구체적인 예를 날리면 인터뷰한 의미가 없습니다.

### 소개문이 클릭을 가른다

본문이 아무리 좋아도 목록에서 안 눌리면 안 읽힙니다. 그런데 소개문은 보통 마지막에 급하게 씁니다.

그래서 본문과 같이 만듭니다. **150자 이내**, 앞 **80자** 안에 문제를 끝냅니다 — 목록 카드에서 실제로 보이는 건 거기까지입니다. 새로 쓰지 않고 **본문 도입부를 압축**합니다. 요약이 본문과 다른 약속을 하면 들어온 독자가 바로 나갑니다.

"~를 살펴봅니다", "~한 경험을 공유합니다"는 목차 안내지 소개문이 아닙니다.

### 플레이스홀더를 남긴 채 끝내지 않는다

`[여기 채우기]`가 적힌 채로 발행된 적이 있습니다. 그래서 마지막에 눈으로 넘겨짚지 않고 `grep -c`로 셉니다.

### 트러블슈팅에는 정해진 순서가 있다

삽질 소재가 있으면 4장 "개발하며 부딪힌 문제"에 넣습니다. 원인만 쓰면 매뉴얼이고, **왜 그 선택을 했는지**를 써야 글이 됩니다. 실패 구간마다 이 골격을 씁니다.

> 증상 → 의심 범위 좁히기 → 확인한 것 → 원인 → **판단**

"의심 범위 좁히기"가 독자에게 제일 쓸모 있는 부분입니다. "로컬은 되는데 배포는 안 된다면 남는 건 실행 환경의 차이다" 같은 추론은 독자가 자기 상황에 그대로 가져다 쓸 수 있습니다.

## 다른 스킬과의 관계

| 스킬 | 역할 |
| :--- | :--- |
| **blog-post** | 뭘 쓸지 정하고, 사실을 모으고, 초안을 만든다 |
| `humanize-korean` | 완성된 초안의 문체에서 AI 티를 벗긴다 (내용은 안 건드림) |
| `claude-in-chrome` | 실제 화면을 캡처한다 |

`humanize-korean`은 내용을 추가·삭제하지 않습니다. 그래서 **초안 단계에서 내용을 완성해두고** 넘겨야 합니다.

## 주의

- 초안은 로컬 `.md`로만 남깁니다. 커밋은 요청받았을 때만 합니다.
- `humanize-korean`은 cwd에 `_workspace/`를 만듭니다. 레포 안에서 돌렸다면 커밋에 섞이지 않았는지 확인하세요.
- 스크린샷에 실계정·토큰·고객사 정보가 찍혔는지는 **사람이** 확인해야 합니다. 스킬은 가려야 할 곳을 지적할 뿐 대신 가려주지 않습니다.
