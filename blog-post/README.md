# blog-post

레포에서 **글로 남길 만한 것**을 찾아 후보를 제안하고, 고른 주제로 기술 블로그 초안을 만듭니다. 화면은 실제로 캡처해서 넣고, 마지막에 AI 티를 벗깁니다.

```
/blog-post
```

## 무엇을 하나

1. **글감 발굴** — git 히스토리에서 마찰의 흔적을 찾습니다. revert·재수정 커밋, 통째로 갈아엎은 구조, 유난히 자주 손댄 파일, 새로 들어온 의존성. 기능 목록이 아니라 "예상과 달랐던 것"을 찾습니다.
2. **후보 제안** — 3~4개를 제목안·줄거리·근거 커밋과 함께 물어봅니다. 쓸 게 없으면 없다고 합니다.
3. **사실 수집** — 고른 주제에 대해 실제 코드·커밋·설정을 읽습니다. 확인된 것과 확인 못 한 것을 나눠 관리합니다.
4. **스크린샷** — `claude-in-chrome`으로 새 탭을 열어 캡처합니다. 폭을 고정해서 샷 크기를 맞추고, 실계정·토큰이 찍혔는지 확인합니다.
5. **초안** — PAS(문제 → 심화 → 해결 예고)로 열고, `template.md` 골격을 채웁니다.
6. **AI 티 제거** — `humanize-korean`에 넘깁니다.
7. **점검** — 이미지 수, 제목 밀도, 플레이스홀더 잔존을 `grep`으로 셉니다.

## 왜 이렇게 설계했나

### 없는 사실을 만들지 않는다

글감을 키우다 보면 구체적인 숫자가 아쉬워집니다. "이틀은 아꼈다", "3배 빨라졌다" 같은 문장은 글을 그럴듯하게 만들지만, 근거가 없으면 그냥 거짓말입니다. 실제로 초안을 만들다 없는 기간과 없는 리전명을 넣은 적이 있습니다.

그래서 **확인된 사실은 파일·줄 번호와 함께, 확인 못 한 것은 본문이 아니라 "직접 채울 것" 목록으로** 분리합니다. 빈칸이 틀린 값보다 낫습니다.

### AI 티를 벗기다가 가독성을 죽이지 않는다

AI가 쓴 글은 이모지가 문장마다 붙고, 굵게+콜론 불릿이 연속되고, 표가 남발됩니다. 그래서 이걸 전부 걷어내면 문체는 자연스러워집니다 — 그리고 **아무도 안 읽는 텍스트 벽**이 됩니다.

문제는 이 장치들이 *남발*된 거지 존재한 게 아닙니다. 훑어읽는 독자에게는 붙잡을 앵커가 필요합니다. 그래서 정량 게이트를 둡니다.

| 항목 | 기준 |
| :--- | :--- |
| 이미지 | 1장 이상, 각각 아래 한 줄 캡션 |
| 연속 텍스트 문단 | 한 화면(4~5개) 넘으면 이미지·코드·표 삽입 |
| 문단 길이 | 3~4줄에서 끊기 |
| 코드블록 | 연속 15줄 이내 |
| `h3` 개수 | `h2` 하나당 최대 2개 |
| 굵게 | 섹션당 1~3회 |
| 이모지 | 제목·섹션 라벨에만 |

`humanize-korean`을 통과한 **뒤에** 이 게이트를 다시 확인합니다. 윤문 과정에서 시각 요소가 깎이기 때문입니다.

기준이 "문단 5개"가 아니라 "한 화면"인 이유가 있습니다. velog·티스토리는 단이 좁아서, 에디터에서 4줄이던 문단이 발행본에선 8줄이 됩니다. 원고에서 멀쩡해 보이던 구간이 실제로는 스크롤 한 번이 통째로 글자입니다. 그래서 발행 후 실제 페이지를 한 번 내려보라고 안내합니다.

### 도입부에서 이탈이 갈린다

목록에서 클릭해 들어온 사람은 첫 화면만 보고 나갈지 정합니다. 그래서 "X는 ~하는 서비스입니다"로 열지 않고 **문제 → 심화 → 해결 예고** 순으로 엽니다. 배경은 문제를 던진 다음에 필요한 만큼만 넣습니다. 제목도 "~를 해보았습니다"보다 구체적인 이득·손실이 앞에 와야 클릭됩니다.

이건 숏폼의 리텐션 구조와 같습니다. 숏츠가 첫 3초에 이탈이 갈리는 것처럼 글은 첫 화면에서 갈리고, 대응도 같은 역삼각형입니다 — 결론을 아끼지 않고, 포인트는 3개까지만, 마지막엔 도입부 문제로 되돌아와 닫습니다(루프). 곁가지 주제는 다른 글로 뺍니다.

### 플레이스홀더를 남긴 채 끝내지 않는다

`[여기 채우기]`가 적힌 채로 발행된 적이 있습니다. 그래서 마지막에 눈으로 넘겨짚지 않고 `grep -c`로 셉니다.

### 트러블슈팅에는 정해진 순서가 있다

원인만 쓰면 매뉴얼이고, **왜 그 선택을 했는지**를 써야 글이 됩니다. 실패 구간마다 이 골격을 씁니다.

> 증상 → 의심 범위 좁히기 → 확인한 것 → 원인 → **판단**

"의심 범위 좁히기"가 독자에게 제일 쓸모 있는 부분입니다. "로컬은 되는데 배포는 안 된다면 남는 건 실행 환경의 차이다" 같은 추론은 독자가 자기 상황에 그대로 가져다 쓸 수 있습니다.

## 다른 스킬과의 관계

| 스킬 | 역할 |
| :--- | :--- |
| **blog-post** | 뭘 쓸지 정하고, 사실을 모으고, 초안을 만든다 |
| `humanize-korean` | 완성된 초안의 문체에서 AI 티를 벗긴다 (내용은 안 건드림) |
| `claude-in-chrome` | 실제 화면을 캡처한다 |

`humanize-korean`은 내용을 추가·삭제하지 않습니다. 그래서 **초안 단계에서 내용을 완성해두고** 넘겨야 합니다.

## 주의

- 초안은 로컬 `.md`로만 남깁니다. 커밋은 요청받았을 때만 합니다.
- `humanize-korean`은 cwd에 `_workspace/`를 만듭니다. 레포 안에서 돌렸다면 커밋에 섞이지 않았는지 확인하세요.
- 스크린샷에 실계정·토큰·고객사 정보가 찍혔는지는 **사람이** 확인해야 합니다. 스킬은 가려야 할 곳을 지적할 뿐 대신 가려주지 않습니다.
