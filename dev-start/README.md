# dev-start

티켓 하나를 **이슈 생성 → 기본 브랜치에서 브랜치 → 설계 승인 → 구현 → 검증 → Postman 컬렉션 → 마무리 정리**까지 같은 순서, 같은 품질로 반복하게 만드는 스킬입니다.

## 뭘 하는지

```
1 이슈 → 2 브랜치 → 3 설계(승인 게이트) → 4 구현 → 5 검증 → 6 API 컬렉션 → 7 정리 보고
```

- 3단계는 `superpowers:brainstorming`, 6단계는 `postman-collection-from-code`를 호출합니다. 이 스킬은 둘을 **언제 부르는지**를 정하는 오케스트레이터입니다.
- 7단계 보고는 `template.md` 골격(변경 내역 / 검증 결과 / 직접 할 일 / 확인 필요 / 아직 안 한 것)으로 고정됩니다.
- 커밋·푸시는 요청받았을 때만, 통합 브랜치 반영은 `merge-safe`로 넘깁니다.

## 왜 이렇게 설계했나

### 설계를 보여준 것 ≠ 구현한 것

실제로 있었던 일입니다. 필드를 추가하는 설계안을 제시하고 승인을 기다리는 사이, 사용자는 반영된 줄 알고 마이그레이션을 재실행했습니다. 결과는 새 컬럼이 없는 테이블이었습니다. 그래서 설계를 낸 응답에는 **"아직 코드는 수정하지 않았습니다"를 반드시 적도록** 했고, "했어?"라는 질문엔 기억이 아니라 `git status`로 답하게 했습니다.

### 마이그레이션은 파일로, 운영 전이면 합친다

콘솔에서 친 SQL은 다른 환경에서 재현되지 않습니다. 반대로 아직 운영에 안 나간 기능에 요구사항이 추가될 때마다 마이그레이션 파일을 늘리면 운영 배포 때 지저분한 이력이 남습니다. 운영 전이면 같은 파일에 합치되, **이미 실행한 DB는 메타 테이블 때문에 재실행되지 않으므로** undo → migrate 명령을 사용자 할 일에 넣습니다.

### 직접 할 일은 명령으로 준다

"CORS 설정을 추가하세요"는 할 일이 아니라 숙제입니다. 복붙 가능한 명령, 명령으로 안 되는 건 어느 화면에서 뭘 바꾸는지, 그리고 롤백 방법까지 적습니다.

### 실행 안 한 검증은 "미실행"

타입 체크를 돌렸는지, 런타임 호출을 해봤는지를 보고서에서 분리합니다. `npx`가 로컬이 아닌 동명의 패키지를 받아와 exit 0으로 통과해버리는 경우가 있어서, 로컬 바이너리를 직접 호출하도록 했습니다.

## 쓰는 법

```
이 기능 개발 시작하자. 이슈부터 만들어줘
<ISSUE-KEY>로 브랜치 따서 진행해줘
다 끝났으면 정리하고 내가 해야 할 거 알려줘
```

## 안 쓰는 경우

- 티켓 없이 끝나는 한 줄 수정
- 장애 원인 추적이 먼저인 디버깅 작업
