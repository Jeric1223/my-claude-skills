# dev-start

## Overview

티켓 하나를 **이슈 → 브랜치 → 설계 승인 → 구현 → 검증 → API 문서 → 마무리 정리**까지 한 사이클로 끝낸다. 각 단계는 앞 단계의 산출물이 있어야 넘어간다.

핵심 원칙: **설계를 보여준 것과 구현한 것은 다른 상태다.** 두 상태를 사용자가 헷갈리지 않게 매 응답에서 분명히 한다.

## When to Use

- 새 기능·API·스키마 변경을 이슈 트래커 티켓 단위로 시작할 때
- 개발이 끝나서 변경 내역과 사용자가 직접 해야 할 일을 정리할 때 (5~7단계만 수행)

**Not for:** 오타 수정 같은 티켓 없는 한 줄 변경, 장애 대응(→ systematic-debugging 계열).

## 사이클

```
1 이슈 → 2 브랜치 → 3 설계(승인 게이트) → 4 구현 → 5 검증 → 6 API 컬렉션 → 7 정리 보고
                                                          └→ (요청 시) 커밋·푸시 → 통합 브랜치 반영
```

### 1. 이슈를 만든다

- 이슈 트래커 MCP(Jira 등)가 연결돼 있으면 그걸로 생성하고, 없으면 사용자에게 이슈 키를 받는다.
- 제목은 결과물 기준 한 줄 ("보고서 PDF 업로드/다운로드 API 개발"), 설명엔 배경·범위·제외 범위.
- 생성은 외부 쓰기다. 제목·프로젝트를 보여주고 승인받은 뒤 만든다.

### 2. 기본 브랜치에서 브랜치를 딴다

```bash
git fetch origin
git switch -c <ISSUE-KEY>-<짧은-요약> origin/<master|main>
```

- 로컬 master가 아니라 **`origin/<기본브랜치>`** 에서 딴다. 로컬이 뒤처져 있으면 머지 때 엉뚱한 diff가 딸려온다.
- 작업트리가 더러우면 멈추고 알린다. 남의 변경을 새 브랜치로 끌고 가지 않는다.

### 3. 설계하고 승인받는다

- `superpowers:brainstorming`을 호출해 spike / bounded / architectural로 분류한다.
- 결과물이 갈리는 것만 AskUserQuestion으로 묻는다. 이런 류가 전형적이다:
  - 데이터 소유 범위 (전역 / 조직별 / 사용자별)
  - 권한 (누가 쓰고 누가 읽나)
  - 필수 여부, 이미 실행된 마이그레이션을 어떻게 처리할지
- 설계는 "파일별로 뭘 바꾸는지 + 사용자가 수동으로 할 인프라 작업"까지 포함한다.
- **설계를 제시한 응답에는 `아직 코드는 수정하지 않았습니다`를 명시하고 멈춘다.** 승인 전 구현 금지.
- spec/plan md 문서는 로컬에만 둔다. 커밋하지 않는다 (사용자 규칙이 다르면 그걸 따른다).

### 4. 구현한다

- 레포의 가장 비슷한 기존 기능을 먼저 찾아 **그 구조(model / repository / service / controller, 권한 맵, 라우트 등록 위치)를 그대로** 따른다. 새 패턴을 만들지 않는다.
- 스키마 변경은 **마이그레이션 파일**로 만든다. 콘솔에서 치는 SQL로 넘기지 않는다.
- 요구사항이 중간에 바뀌었고 그 마이그레이션이 **아직 운영에 안 나갔으면** 새 파일을 추가하지 말고 같은 파일에 합친다. 이때 이미 실행된 DB가 있는지 사용자에게 확인하고, 있으면 7단계에 `undo → migrate` 재실행을 적는다.
- 사용자가 "했어?"라고 물으면 기억이 아니라 `git status`/`git diff`로 확인하고 답한다.

### 5. 검증한다

- 타입 체크·린트·빌드 중 레포가 쓰는 것을 **실제로 실행**하고 exit code를 본다. 출력이 비었다고 통과로 보지 않는다.
- `npx <tool>`이 로컬 패키지가 아닌 걸 받아올 수 있으니 `node node_modules/<pkg>/bin/<bin>` 형태를 우선한다.
- 마이그레이션 JS는 최소 `node -e "require('./<file>')"`로 문법을 확인한다.
- 실행하지 못한 검증은 "미실행"으로 적는다. 런타임 호출을 안 했으면 안 했다고 쓴다.

### 6. API 컬렉션을 만든다

- 엔드포인트가 생기거나 바뀌었으면 `postman-collection-from-code` 스킬을 호출한다.
- 필드가 추가되면 컬렉션 변수·요청 body·응답 예시·에러 설명을 **같이** 고친다. 코드만 바뀌고 컬렉션이 낡는 게 가장 흔한 누락이다.

### 7. 정리 보고를 낸다

`template.md` 골격대로 쓴다. 섹션을 빼지 말고, 해당 없으면 "없음"이라고 적는다.

사용자가 직접 해야 할 일은 **복붙 가능한 명령**으로 준다. 클라우드 콘솔 작업처럼 명령으로 줄 수 없는 것은 어느 화면에서 무엇을 바꾸는지 적는다. 운영 리소스·클라우드 쓰기는 직접 실행하지 않는다.

### (요청 시) 커밋·푸시와 통합 브랜치 반영

- 커밋·푸시는 사용자가 요청했을 때만 한다. 커밋 대상 파일을 명시적으로 `git add <path>`하고, spec/plan 문서·`.env`는 제외한다.
- test/dev 같은 통합 브랜치에 넣어야 하면 `merge-safe` 스킬로 넘긴다.
- 푸시 후 보안 리뷰 같은 자동 경고가 오면, 이번 변경에서 나온 건지 통합 브랜치에 원래 있던 코드인지 구분해 보고한다.

## Common Mistakes

| 실수 | 결과 |
| --- | --- |
| 설계안을 제시하면서 "수정 안 했음"을 안 적음 | 사용자가 반영된 줄 알고 DB를 재생성 → 새 컬럼 없는 테이블 |
| 로컬 master에서 브랜치 생성 | 오래된 기준점, 머지 때 무관한 diff |
| 이미 실행된 마이그레이션 파일만 고침 | 메타 테이블에 기록돼 있어 재실행 안 됨 — undo 안내 필요 |
| 필드 추가 후 API 컬렉션 미갱신 | 프론트가 400을 받고 원인 문의 |
| 검증 안 하고 "완료" | 첫 배포에서 타입 에러 |
| "내가 할 일"을 설명문으로만 줌 | 사용자가 명령을 다시 조립하다 실수 |
