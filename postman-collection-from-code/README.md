# postman-collection-from-code

API를 만들거나 고친 직후, **소스에서 읽어** Postman 컬렉션 JSON을 만듭니다. 그대로 import하면 되고, 받는 사람이 파라미터 값을 되묻지 않습니다.

## 뭘 하는지

라우터 → 검증 스키마 → enum → 인증 미들웨어 → 리포지토리 순서로 5군데를 읽고, 거기서 나온 사실만으로 컬렉션을 채웁니다. 확인 못 한 건 채우지 않고 `※ 확인 필요`로 남깁니다.

결과물의 특징은 **설명이 파라미터 옆에 붙는다**는 것입니다.

```jsonc
{
  "key": "progressCode",
  "value": "PENDING",
  "description": "진행 상태. 미전달 시 전체 조회.\nPENDING 대기 | RUNNING 진행 | HOLD 보류 | REVIEW 검토\n※ 종료일시 정렬은 종료 상태와 같이 써야 의미가 있다"
}
```

Postman의 Params 탭에는 Description 열이 있습니다. 여기에 값이 있으면 요청을 수정하는 화면에서 바로 보이고, 컬렉션 설명에 몰아쓰면 아무도 안 봅니다.

## 왜 이렇게 설계했나

### 인증 방식을 옆 컬렉션에서 복붙하지 않는다

같은 레포의 다른 API가 `Authorization: Bearer`를 쓴다고 이 라우트도 그렇다는 보장이 없습니다. 실제로 이름이 JWT처럼 보이는 미들웨어가 헤더가 아니라 signed cookie를 읽고 있어서, 관례대로 Bearer를 넣었으면 컬렉션 전체가 401만 뱉을 상황이 있었습니다.

그래서 절차에 **미들웨어 본문을 열어 어디서 토큰을 읽는지 확인**하는 단계를 못 박았습니다. 5군데 중 가장 자주 생략되는 곳입니다.

### "허용된 값만 사용 가능합니다"는 설명이 아니다

검증 스키마의 에러 메시지를 그대로 옮기면 이런 문장이 나옵니다. 받는 사람은 그 값이 뭔지 몰라서 결국 물어봅니다. enum 파일까지 따라가서 **코드와 한글 라벨을 전부 나열**하게 했습니다. 지역 코드 13개, 상태 코드 7개를 적는 데 드는 비용보다 왕복 한 번이 비쌉니다.

### 파라미터가 아닌데 결과를 바꾸는 것들

코드에 하드코딩된 제외 조건 — 특정 상태값 제외, 특정 조합 제외 — 은 Params 탭에 자리가 없습니다. 그래서 빠뜨리기 쉽고, 빠지면 "필터 걸었는데 0건"의 원인을 아무도 못 찾습니다. request description에 `■ 조회 제외 규칙 (파라미터 아님, 항상 적용)` 섹션으로 반드시 남깁니다.

### 설명을 3층으로 나눈다

같은 내용을 두 곳에 쓰면 한쪽이 낡습니다. **무엇에 대한 설명인가**로 위치를 정합니다.

| 위치 | 담는 것 |
| :--- | :--- |
| collection description | API군 전체, 유사 API와의 차이, 인증, 공유 코드표 |
| query[].description | 그 파라미터 하나 |
| request description | 서버측 제외 규칙, 고정 동작, 응답 구조, 에러 코드 |

### 갱신이 기본, 생성이 예외

API 수정 요청은 대부분 이미 있는 컬렉션의 갱신입니다. 새 파일을 만들면 두 벌이 돌아다니면서 어느 게 최신인지 알 수 없게 됩니다. 먼저 기존 컬렉션을 찾고, 해당 item만 고치고, 바뀐 파라미터만 손대고, 삭제된 파라미터는 지웁니다.

## 쓰는 법

API를 만들거나 고친 뒤에 이렇게 말하면 됩니다.

```
포스트맨 컬렉션 만들어줘
방금 고친 API 컬렉션에 반영해줘
프론트한테 넘길 수 있게 json으로 뽑아줘
```

저장 위치는 레포에 기존 컬렉션이 있으면 그 관례를 따르고, 없으면 물어봅니다.

## 안 쓰는 경우

- 소스에 OpenAPI/Swagger 스펙이 이미 있는 프로젝트 — Postman이 그걸 직접 import합니다
- 소스가 없는 외부 서드파티 API — 읽을 곳이 없으면 결국 추측이 됩니다
