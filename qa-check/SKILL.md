# qa-check

## Overview

합동 QA에는 개발자가 아닌 사람들이 들어온다. 이들은 "버그"보다 **"이게 무슨 뜻이지?"**, **"왜 이렇게 눌러야 하지?"** 를 더 많이 적는다. 개발자는 이미 뜻을 알고 있어서 이런 걸 스스로 못 찾는다.

핵심 원칙: **코드가 아니라 화면에서 시작한다. 직접 열어서 본 것만 이슈로 쓴다.** 댓글이나 기억만으로 "재현됨"이라고 쓰지 않는다.

## When to Use

- 배포된 dev/staging 사이트를 화면 단위로 점검해 QA 시트 행으로 남길 때
- QA 시트의 댓글이 지금 사이트에서 실제로 보이는지 확인할 때

**Not for:** 코드 위치 찾기·수정 (재현 판정이 끝난 뒤에 별도로), 자동화 E2E 테스트 작성.

## 절차

### 1. 접근 방식 먼저 정한다

- 브라우저(`claude-in-chrome`)에 **이미 로그인된 세션이 있으면 그대로 쓴다.**
- 로그인 화면이면 멈추고 사용자에게 직접 로그인해달라고 한다. **대화창에 붙여준 ID/비밀번호도 입력하지 않는다** (로컬 개발 호스트가 아니면 자격증명 입력은 금지). 비밀번호는 산출물에도 남기지 않는다.
- 쓰기 동작(제출·삭제·다운로드 확정)은 하기 전에 묻는다. 조회·탭 전환·모달 열기까지만 자유.

### 2. 점검 대상을 좁힌다

화면 경로(`메뉴 > 화면 > 패널 > 탭`)를 하나 잡는다. 시트 댓글이 있으면 그 경로부터, 없으면 사용자가 지정한 화면부터. 한 번에 전체를 돌지 않는다.

데이터 이슈는 **설비명/업체명/식별번호**가 있어야 재현된다. 댓글에 없으면 쓰지 말고 요구한다. 빈 값은 데이터가 없는 건지 화면 버그인지 구분이 안 된다.

### 3. 헷갈림 체크리스트로 훑는다

각 화면에서 아래를 **직접 눈으로** 확인한다. 외부 사용자가 실제로 걸린 패턴이다.

| # | 패턴 | 확인할 것 |
|---|------|-----------|
| 1 | 용어·라벨 | 처음 보는 사람이 뜻을 아는가. 같은 말이 화면마다 다른가. 이름이 이상한 조합(예: 사업장 단위 용어가 설비에 붙음) |
| 2 | 빈 값의 의미 | `-`, `0`, `0.0`이 "데이터 없음 / 정상 0 / 미지원" 중 무엇인지 알 수 있는가 |
| 3 | 설명 부재 | 차트·컬럼·코드값(예약/취소 같은 사유)에 헤더·툴팁·범례·단위가 있는가. 같은 목록이 화면마다 헤더가 있다 없다 하는가 |
| 4 | 지표 방향성 | 값이 오르면 좋은 건지 나쁜 건지(부채비율 등)가 색·화살표·카테고리와 모순되지 않는가 |
| 5 | 기본값·일관성 | 탭/화면마다 기본 기간이 다른가. 기본값이 버튼 옵션에 없는가. 같은 지표의 비교 기준이 섞이는가. 기본값으로 돌아갈 방법이 새로고침뿐인가 |
| 6 | 동선 | 클릭이 불필요하게 중복되는가(버튼 → 항목 1개짜리 드롭다운 → 모달). 이동 후 돌아올 방법이 있는가 |
| 7 | 피드백 | 로딩·렌더링 중 표시, 데이터 있는데 "없음" 메시지, 선택 가능/불가 날짜의 시각 구분 |
| 8 | 시각 | 색 구분이 약한 범례, 의미 없는 그라데이션·보조선, 축 시작값·눈금 단위가 데이터 범위와 맞는가 |

체크리스트에 없는 이상한 점도 적는다. 위 표는 시작점이지 한계가 아니다.

### 4. 판정한다 (댓글이 있을 때)

| 판정 | 기준 |
|------|------|
| 재현됨 | 지금 화면에서 그대로 보인다. 본 화면·값을 같이 적는다 |
| 이미 반영된 듯 | 댓글과 달리 지금은 다르다. 다른 데이터에서도 그런지 한 번 더 확인 필요라고 적는다 |
| 확인 불가 | 식별 정보가 없거나 권한/데이터가 없어 못 봤다. 왜 못 봤는지 쓴다 |
| 의도 확인 필요 | 재현은 되지만 버그인지 디자인 의도인지 사람이 정해야 한다 |

"내부 회의 안건" 같은 근거만 있는 댓글은 화면으로 판정하지 않고 **그대로 전달**만 한다.

### 5. 시트 행으로 쓴다

`template.md` 형식을 따른다. `수정 필요`(명백한 오류)와 `확인 필요`(의도·의미 질문)를 구분한다. 제안은 한 가지만 쓴다.

### 6. 말한다

끝에 반드시:
- 직접 본 화면 / 못 본 화면
- 판정별 개수
- 사용자가 어떤 유형에서 가장 헷갈렸는지 (체크리스트 번호로)

## Common Mistakes

- 댓글을 읽고 화면을 안 열었는데 "재현됨"으로 쓴다
- 코드부터 뒤져서 "원래 이렇게 만든 것"이라며 이슈를 기각한다 — 사용자가 모르면 이슈다
- 빈 값을 데이터 이슈 vs 화면 버그로 가르지 않고 섞는다
- 비밀번호를 입력하거나 산출물·메모리에 옮겨 적는다
- 한 행에 이슈 여러 개를 몰아 쓴다
- 이미 고쳐진 걸 오래된 댓글만 보고 "수정 필요"로 남긴다
